# shredder-tspu-monitor

Периодически получает список активных нод из Remnawave, проверяет доступность `IP:порт` через Check-Host из разных стран и отправляет Telegram-уведомление только при смене состояния.

## Как учитывается динамическая проверка

Сервис не считает первый ответ Check-Host итогом. Он:

1. вызывает `GET /check-tcp?host=<IP>:<PORT>` и получает `request_id`;
2. опрашивает `GET /check-result/{request_id}`;
3. ждёт, пока выбранные страны вернут результат или истечёт таймаут;
4. считает IP заблокированным при массовой недоступности из разных стран;
6. сохраняет состояние в SQLite и дедуплицирует повторные уведомления.

## Настройка

```bash
cp .env.example .env
mkdir -p data
nano .env
docker compose up -d --build
docker compose logs -f
```

Для Remnawave v3 нужен отдельный API key со scope `nodes:read`. По умолчанию используется `GET /api/nodes` и заголовок `X-API-Key`. Если у вашей панели внешний API опубликован под другим base path, задайте `REMNAWAVE_API_PATH`.

`CHECKHOST_TYPE` по умолчанию равен `tcp`, а `CHECKHOST_PORT` равен `443`, потому что Reality-ноды принимают TCP. Агентский порт Remnawave Node (`2222`) здесь не проверяется. `Connection refused` не считается блокировкой IP: адрес достижим, но сервис на порту отклонил соединение. Это сохраняется отдельно как `service_refused`.

Для Telegram-топика используются `TELEGRAM_CHAT_ID` и `TELEGRAM_MESSAGE_THREAD_ID`. Для ссылки вида `https://t.me/c/3780243318/2815/2816` это `-1003780243318` и `2815` соответственно.

## Поведение уведомлений

- `clean -> blocked`: отправляется тревога;
- `blocked -> clean`: отправляется сообщение о восстановлении;
- `uncertain` и ошибки: состояние не меняют и тревогу не создают;
- новые ноды автоматически попадают в следующий цикл;
- отключённые ноды не проверяются.
